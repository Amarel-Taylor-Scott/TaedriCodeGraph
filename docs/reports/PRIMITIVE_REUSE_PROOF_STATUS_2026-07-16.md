## Evidence ladder

Taedri is now at the second rung:

1. **Contracts exist** — necessary but not evidence of reuse.
2. **Mechanism works** — now proven for release, search, exact wiring, and deterministic
   two-step execution.
3. **Task benefit** — next: matched real tasks show correctness, token, latency, or cost
   improvement after all Taedri overhead.
4. **Population benefit** — multiple packages, teams, languages, and failure strata.
5. **Economic benefit** — retained customer value exceeds hosting, verification,
   curation, support, and false-selection costs.

The honest confirmation is therefore: Taedri has crossed from an architecture-only POC
to an executable reusable-component mechanism. It has not crossed from mechanism proof
to a generalized savings claim.

## Current decision path

The proven narrow path is:

1. A privacy-scoped trigger decides whether search should run and records only the
   intent digest.
2. Registry search returns active releases; candidates and revoked releases cannot
   enter the shortlist.
3. Declared capability-group labels help retrieval, but do not prove compatibility.
4. The exact planner compares canonical port schemas, shared transports, runtime,
   call style, determinism, purity, network policy, effects, and every required scalar
   compatibility dimension.
5. Any mismatch is incompatible; any missing required fact is unknown; neither state
   creates an adapter or wire.
6. A successful match produces a content-addressed plan, downloads and verifies the
   exact packs, binds execution fields back to each graph digest, executes, and emits a
   content-addressed result receipt.

This separation is deliberate: ranking nominates; typed compatibility connects;
execution and verification decide whether the route worked.

## Safe self-tuning boundary

Self-tuning is not online in the current system. When introduced, it must change only
candidate nomination and ranking—not contracts, evidence, release state, compatibility
truth, or acceptance gates. The first admissible loop is offline and rollbackable:

1. retain immutable query, lane, rank, selection, execution, and verifier receipts;
2. split data by time and source before fitting to prevent answer/task leakage;
3. learn or search weights on the training split only;
4. compare the proposed policy with the current version on a frozen failure-inclusive
   relevance and execution set;
5. publish a signed/versioned ranking policy only after predeclared subgroup gates;
6. shadow it first, retain the prior policy, and roll back on relevance, safety, cost,
   latency, or abstention regression.

Until those receipts and frozen judgments exist, fixed explainable RRF/waterfall
weights are preferable to a model that calls itself self-tuning without evidence.

## Next primitive cohort

Add primitives one at a time, beginning with low-risk, pure, deterministic, unary or
small-record transforms whose behavior is easy to independently verify. Good first
cohort candidates are URL normalization, stable slug generation, bounded retry-delay
calculation, ISO timestamp parsing, digest verification, mapping-key selection, and
validated identifier normalization. Avoid database writes, network calls, credentials,
framework lifecycle hooks, and large dependency closures until isolation, effect
semantics, and route verification are stronger.

Every new primitive must add a real task receipt. An initial, revisable operating
hypothesis is to begin group/orphan/duplicate analysis after roughly 20–50 accepted
primitives, then freeze the first relevance set and evaluate learned or self-tuned
ranking offline after roughly 100. Those numbers are planning triggers to validate,
not empirical thresholds or permission to weaken a release.
